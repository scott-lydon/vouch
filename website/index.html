Vouch

Agentic Model-Based Testing pipeline.

A developer hands off a built artifact (a URL, an iOS .app, an Android .apk, or a screenshot) plus the System Under Test's spec. Vouch deterministically enumerates the interactable surface, learns the Finite State Machine (FSM) over actions purely from observation, asks a cheap Large Language Model to translate the spec into a post-condition predicate per action, runs all permutations against fresh System Under Test instances in a background worker, and reports verdicts. Classical Model-Based Testing requires humans to write both the FSM and the oracles; Vouch infers both. The developer never authors a transition rule.

The architectural identity
Two feedback loops, one strict invariant.
  • Learning loop (left): the Rule Inducer reads surface deltas from the Executor and feeds the Sequence Enumerator on the next run. Each pass gets a denser FSM without anyone editing YAML.
  • Audit loop (right): every stage writes to SQLite. A grep through vouch.db can always answer "why is this rule in its current status."
  • The invariant: the developer never authors a transition rule. If a contributor proposes vouch.rules.yaml, the change is rejected at review. The whole point is to discover the FSM rather than declare it.

The problem this addresses

Classical Model-Based Testing has two human-authored prerequisites: the developer hand-writes the Finite State Machine and the test author hand-writes the oracles. The activation energy is high enough that almost no one uses Model-Based Testing in practice. Hand-written tests catch the path the test author thought of; Model-Based Testing catches the permutations they didn't.

Without Vouch

Classical Model-Based Testing

  • • Developer hand-writes the FSM in YAML or DSL
  • • Test author hand-writes oracle per action
  • • FSM goes stale within a week of the next refactor
  • • Spec drift invalidates oracles silently
  • • Activation energy is high; teams don't adopt
  • • The path the test author imagined is the only path covered
With Vouch

Agentic, inferred Model-Based Testing

  • • FSM is discovered by the Rule Inducer purely from observation
  • • Oracles inferred from spec.md by a cheap Large Language Model (Haiku)
  • • Cache key includes spec_version, so spec edits invalidate the right oracles automatically
  • • Rules promote only after 10 confirmations across 3 distinct runs and 2 calendar days
  • • Pairwise enumeration covers most multi-step regressions for a fraction of the cost
  • • Clash Arbiter classifies a rule break as regression vs. intentional spec evolution

Architecture topology

Six components arranged as a downward main spine with one learning feedback loop on the left (Rule Inducer → Sequence Enumerator) and one side-channel on the right (every stage writes to SQLite). The Clash Arbiter is triggered by the Rule Inducer when a promoted rule starts to deny. The persistence column on the far right is read and written by every stage that needs durable state.

The six components

Each component does exactly one thing well (Unix philosophy) and exposes a typed boundary another component can mock (Composable). The CLI is the only orchestrator; everything else is a subprocess or a pure module.

1. Surface Mapper

Per-platform subprocess that walks the System Under Test and emits surface.json — the set of interactable nodes with stable selectors. Web uses Playwright, iOS uses XCUITest, Android uses Appium 2, Image uses Anthropic vision.

PROS
  • Native introspection per platform; no fragile heuristics
  • Stable selectors prefer data-testid > ARIA role+name > CSS path
  • Single NDJSON contract across all four platforms
CONS
  • Four executor codebases to maintain
  • Image executor's accuracy depends on vision model quality

2. Sequence Enumerator

Pure function (Surface, PromotedRules, Strategy) → Plan. Reads promoted rules from vouch.db (empty on a fresh project — that's the bootstrap case). Emits plan.json with one permutation per row.

PROS
  • Pure function; same inputs → same outputs (Predictable)
  • Pairwise (PICT covering array) catches most multi-step bugs
  • Exhaustive capped at 100,000 sequences with a clear error past the cap
CONS
  • Pairwise misses some 3-way interactions by design
  • Exhaustive blows up combinatorially past the cap

3. Oracle Translator

For each (action, pre-state) pair, calls Claude Haiku 4.5 once to translate spec.md into a PostConditionPredicate from a closed DSL of nine kinds. Cache key includes spec_version, so a spec edit invalidates only the affected rows.

PROS
  • Cheap (Haiku) and capped by the cache
  • Predicate DSL is closed; LLM never emits executable code
  • Spec-section invalidation recomputes only overlapping headings
CONS
  • Ambiguous spec text can produce a wrong-but-plausible predicate
  • Cache stats panel needed to surface this risk to the developer

4. Executor + Verdict Engine

A Swift actor-based worker pool runs permutations against fresh System Under Test instances. Captures pre/post surface snapshots, evaluates the predicate, writes the verdict, emits SurfaceDelta events for the Rule Inducer.

PROS
  • Fresh context per permutation isolates side effects
  • Per-step timeout (30s default); timeout → verdict, never a hung worker
  • Verdict writes batched per sequence (one transaction)
CONS
  • Boot cost per permutation (browser ~200ms, simulator ~5s)
  • iOS executor mitigates with simulator pooling

5. Rule Inducer

The brain. Reads the delta queue, scores candidate rules with a time-weighted Beta-with-decay formula, and promotes or retires under the threshold rule: ≥10 confirmations, <2 denials, ≥3 distinct runs, ≥2 calendar days. The developer never writes a rule; the inducer is the sole writer.

PROS
  • Zero developer setup — rules emerge from observation
  • Time decay (1/(1+age_days)) means yesterday's denial outweighs last year's confirmation
  • Multi-run, multi-day requirement breaks single-run flukes
CONS
  • Promotion latency: ~2 days minimum for new rules to land
  • Thresholds tunable in vouch.config.yaml when bootstrapping

6. Clash Arbiter

Triggered when a previously promoted rule starts to deny. Loads spec.md at the rule's promoted_at commit (git history first, SQLite fallback), diffs against the current spec, and asks Haiku to classify: regression, evolution_intentional, or evolution_possibly_intentional.

PROS
  • Distinguishes "the code regressed" from "the spec changed and the code followed"
  • Every call audited with prompt sha + raw response + cost in arbiter_decisions
  • evolution_intentional auto-retires; possibly_intentional flags for review
CONS
  • Will misclassify some regressions as evolution; the audit row is the smoking gun
  • Developer can override with vouch rules arbitrate <rule_id> --as regression

Honest trade-offs

Every panel below is something the design accepts as a cost, with the trigger that would justify revisiting.

Local-only v1 vs. hosted from day one

Non-developer team members cannot trigger runs themselves.

When it would bite: a designer wants to QA their changes without a terminal.
Trigger to revisit: when more than one non-developer asks.

LLM-inferred oracles vs. hand-written

Some oracle errors (unparseable_oracle verdict, miscalibrated predicate).

When it would bite: spec is ambiguous and the model invents a predicate the developer disagrees with.
Mitigation: vouch cache stats exposes the Large Language Model's effective contribution; developer can override any predicate by editing the cache row.

SQLite vs. Postgres

Worker count bounded by SQLite's writer-serialization.

When it would bite: above 16 concurrent workers writing verdicts.
Mitigation: executor batches verdict writes per sequence (one transaction per sequence). Bottleneck is sequence count, not step count.

Per-permutation fresh System Under Test vs. reusing

Boot cost: browser ~200ms, simulator ~5s, app launch ~1s.

When it would bite: 100 iOS permutations is several minutes of simulator boot.
Mitigation: iOS executor pools simulators (one simulator serves N permutations sequentially with app reset between each).

Pairwise default vs. exhaustive default

Misses some 3-way interactions in the default mode.

When it would bite: a regression that requires three specific actions in a specific order.
Mitigation: --strategy exhaustive --depth 3 is one flag away; the developer chooses when paranoia is required.

Statistical confidence vs. promotion latency

Higher thresholds (10 / 3 / 2) mean rules promote slowly but stay correct.

When it would bite: developer iterating on a brand-new feature wants the inducer to recognize a pattern within a day.
Mitigation: per-project tuning in vouch.config.yaml; drop to 3/2/0 while bootstrapping, raise back later.

Auto-retire vs. always flag-for-human

Auto-retire self-heals; the cost is occasional silently-wrong retirement. We split: evolution_intentional retires, evolution_possibly_intentional flags.

When it would bite: arbiter is overconfident and a rule retires that should not have.
Mitigation: vouch rules ls --status retired_by_spec_change is greppable; arbiter_decisions audit row is the smoking gun.

Spec-diff arbitration vs. test-author judgement

A Large Language Model reading a diff will sometimes misclassify regression as evolution or vice versa.

When it would bite: arbiter labels a real regression evolution_intentional because the spec edit is superficially plausible.
Mitigation: every arbiter call audited with prompt + raw response; developer can replay, override with vouch rules arbitrate <rule_id> --as regression, and the override itself is logged.

Cost model

Vouch makes two Large Language Model calls per unique (action, pre-state): one Haiku call by the Oracle Translator, and (only on a clash) one Haiku call by the Arbiter. Everything else is deterministic. The cache absorbs repeated invocations across runs of the same plan.

Per-run LLM cost (estimated, first run, cold cache)

Estimate assumes: 50 unique actions, 5 unique pre-states per action, 100% cache miss on cold start. Numbers in dollars at published Haiku 4.5 pricing. Once the cache warms, the cost on the second run of the same plan is ~0 (predicates are deterministic per (action, pre-state, spec_version)).

Cache-hit ratio over successive runs (target)

After the first run, unchanged (action, pre-state) pairs hit the cache. The dip on run 4 reflects a hypothetical spec edit invalidating overlapping headings. Spec-section invalidation means a small edit doesn't blow away the whole cache.
